# جدولة معالج انتهاء صلاحية نقاط الولاء (Railway Cron)

هذا الملف توثيق وتوصية فقط — **مفيش جدولة (Railway Cron Job أو غيرها) اتضافت أو
اتفعّلت تلقائياً كجزء من هذا التغيير**. أمر `npm run loyalty:expire` موجود وجاهز، لكنه
مجرد سكريبت يدوي حتى يتم ربطه فعلياً بجدولة خارجية بمعرفة صاحب المشروع.

راجع كمان [`ABANDONED_CART_CRON.md`](./ABANDONED_CART_CRON.md) لنفس التوثيق الخاص
بمعالج تذكير السلة المهجورة.

## لماذا مفيش scheduler جوه التطبيق نفسه

نفس مبدأ `db:cleanup` و`notify:abandoned-cart` الموجودين بالفعل: عملية السيرفر (Express)
مسؤوليتها خدمة الطلبات بس — أي مهمة دورية (تنظيف، تذكير، انتهاء صلاحية) بتُشغَّل كسكريبت
مستقل منفصل تماماً عن عملية السيرفر، بمعرفة جدولة خارجية (Railway Cron Job هنا). ده بيمنع
مشاكل زي: تكرار التشغيل لو أكتر من نسخة (replica) من السيرفر شغّالة في نفس الوقت، أو تعليق
عملية السيرفر الأساسية بمهمة دورية طويلة.

## إعداد Railway Cron Job (خطوات يدوية)

1. من لوحة تحكم Railway → المشروع → أضف خدمة جديدة من نوع "Cron Job" (منفصلة عن خدمة
   الويب الأساسية، بس بتشارك نفس الـ repo/environment variables زي `DATABASE_URL`).
2. Build command: نفس أمر بناء السيرفر الحالي (`npm install && npm run build --prefix server`)
   أو استخدم نفس صورة/بناء خدمة الويب الأساسية لو Railway بيسمح بمشاركتها.
3. Start command: `npm run loyalty:expire --prefix server`
4. متغيرات البيئة المطلوبة: `DATABASE_URL` فقط (نفس القيمة المُستخدمة في خدمة الويب
   الأساسية — بدونها هتفشل فوراً بنفس رسالة الخطأ الموجودة في `db.ts`). لا يوجد أي متغير
   إضافي مطلوب لهذا السكريبت.
5. **الجدولة (Railway Cron Jobs تعمل بتوقيت UTC فقط — لا يوجد إعداد منطقة زمنية لكل
   Job).** التوصية: مرة واحدة يومياً — كافية تماماً لميزة زي دي، مفيش داعي لتكرار أعلى.

   الهدف: حوالي الساعة 3 صباحاً بتوقيت القاهرة (وقت منخفض جداً في حركة الطلبات).
   التحويل لـ UTC مش مؤكد 100% بشكل دائم لأن مصر غيّرت سياسة التوقيت الصيفي أكتر من مرة
   في السنوات الأخيرة (أُلغي 2014، اتفعّل جزئياً تاني في 2023، ثم أُلغي تاني) — يعني
   الفارق بين توقيت القاهرة وUTC مش قيمة ثابتة مضمونة بشكل دائم، وبيعتمد على السياسة
   الرسمية وقت التشغيل الفعلي:

   - لو مصر بتوقيت قياسي ثابت +2 (الحالة الأغلب في السنوات الأخيرة، بدون توقيت صيفي):
     `3:00 صباحاً بتوقيت القاهرة = 01:00 UTC` → عبارة cron: **`0 1 * * *`**
   - لو تفعّل توقيت صيفي (+3) وقت التشغيل: `3:00 صباحاً بتوقيت القاهرة = 00:00 UTC` →
     عبارة cron: `0 0 * * *`

   **التوصية الافتراضية المستخدمة هنا: `0 1 * * *`** (بافتراض +2 ثابت، وهو الوضع
   الأغلب حالياً) — لكن لازم يتأكد صاحب المشروع من السياسة الرسمية الحالية لتوقيت مصر
   وقت إعداد الـ Cron Job فعلياً على Railway، مش الاعتماد على الافتراض ده كحقيقة دائمة.
   التوقيت هنا غير حرج (فرق ساعة واحدة في توقيت تشغيل مهمة تنظيف دورية ليلية لا يؤثر على
   صحة النتيجة أبداً، بس على وقت التشغيل بالظبط).

## التحقق من إن المعالج شغّال صح فعلاً

بعد الربط بالجدولة، راقب لوجات خدمة الـ Cron على Railway بعد أول تشغيلة متوقعة — السكريبت
بيطبع سطر واحد واضح زي:

```
loyalty expiry: processed 12 expired lot(s) across 1 batch(es)
```

لو انتهاء الصلاحية معطّل من إعدادات المتجر (`loyalty_expiry_enabled = false`)، السكريبت
بيطلع "processed 0 expired lot(s)" فوراً من غير أي استعلام قاعدة بيانات إضافي — ده سلوك
متوقع، مش خطأ.

## الأمان تحت التداخل (Overlapping Runs)

لو حصل بالخطأ إن تشغيلتين اشتغلوا في نفس الوقت (تشغيلة يدوية زيادة عن الجدولة، أو تأخير
في التشغيلة السابقة)، `runLoyaltyExpiryBatch` بيستخدم `SELECT ... FOR UPDATE SKIP LOCKED`
على مستوى قاعدة البيانات — يعني كل صف (دفعة نقاط منتهية) بياخده تشغيلة واحدة بس، والتشغيلة
التانية بتتجاوزه تلقائياً بدل ما تنتظر أو تعالجه مرتين. الحماية دي في قاعدة البيانات نفسها،
مش في متغير أو قفل في الذاكرة — فبتفضل صحيحة حتى لو التشغيلتين في عمليتين (processes) منفصلتين
تماماً على أجهزة مختلفة.

## الحالة الحالية (تم التحقق منها فعلياً عبر Railway API)

- **الكود جاهز (CODE READY)**: السكريبت مبني، بيطلع exit code صفر عند النجاح وواحد عند
  الفشل، بدون أي unhandled promise rejection، ومحدود العدد (`MAX_BATCHES`) فلا يمكن أن
  يدخل في حلقة مفتوحة. تم تشغيله يدوياً محلياً والتأكد من ناتجه.
- **Railway Cron: غير مُفعّل (NOT CONFIGURED)** — تم فحص قائمة الخدمات الفعلية على
  مشروع Railway (`bb9f5517-0a26-4320-9796-9735666fe6f9`) وتأكيد وجود خدمتين فقط:
  قاعدة البيانات (Postgres) وخدمة الويب الأساسية. **لا توجد أي خدمة من نوع Cron Job**.
  أي ادعاء بأن انتهاء صلاحية نقاط الولاء "شغّال تلقائياً في الإنتاج" غير صحيح حالياً —
  لازم إعداد يدوي بالخطوات فوق أولاً.
