# صلاحيات مستخدم قاعدة البيانات (Least Privilege)

هذا الملف توثيق وتوصيات فقط — **مفيش أي تغيير تلقائي أو فوري على مستخدم/صلاحيات قاعدة
بيانات الإنتاج على Railway اتعمل أو هيتعمل كجزء من هذه المراجعة**. تدوير أو تغيير بيانات
اعتماد قاعدة بيانات الإنتاج قرار يدوي مقصود لصاحب المشروع، مش شيء يُنفَّذ تلقائياً.

## 1. الوضع الحالي (كما تم تأكيده فعلياً)

- قاعدة بيانات واحدة فقط (PostgreSQL على Railway)، ونفس `DATABASE_URL` بيُستخدم لخطوتين
  مختلفتين تماماً في نفس عملية النشر (`package.json` → `"start"`):
  1. `npm run db:migrate --prefix server` — تنفيذ ملفات الترحيل (`CREATE TABLE`, `ALTER
     TABLE`, `CREATE INDEX`... إلخ)، محتاج صلاحيات DDL.
  2. `node server/dist/index.js` — تشغيل السيرفر نفسه وقت التعامل مع الطلبات، ومحتاج بس
     `SELECT`/`INSERT`/`UPDATE`/`DELETE` على جداول التطبيق (DML)، وأبداً DDL بعد الإقلاع
     (`checkMigrations.ts` بيتأكد من كده، ومحدش في كود التطبيق بيعمل `CREATE`/`ALTER` وقت
     التشغيل).
  - يعني حالياً: **نفس الحساب (role) الواحد** بيُستخدم للاثنين، وعلى الأغلب هو نفس مستخدم
    الـ superuser الافتراضي اللي بترجعه خدمة Postgres المُدارة من Railway (Railway
    بيوفّر instance عادي من Postgres مش "Database as a Service" بأدوار متعددة جاهزة من
    الأول زي RDS مثلاً)، إلا لو حد عدّل ده يدوياً قبل كده.
  - مفيش أي دليل في الكود إن حساب Postgres حالياً مقيّد (scoped) لصلاحيات أقل من كامل
    الصلاحيات على قاعدة البيانات.

## 2. الخطر النظري (وليه الفصل مهم)

لو أي ثغرة (SQL injection غير مكتشفة، RCE في تبعية، إلخ) سمحت لمهاجم بتنفيذ استعلامات
عبر اتصال السيرفر بقاعدة البيانات، فالمهاجم هيورث نفس صلاحيات الحساب المتصل بيه السيرفر.
لو الحساب ده نفسه عنده صلاحيات DDL/superuser (بدل ما يكون مقصور على DML بس)، بقدرة
المهاجم تمتد لتعديل المخطط (schema) نفسه، حذف جداول، إنشاء extensions، أو حتى (لو
superuser فعلي) قراءة/كتابة ملفات على السيرفر عن طريق `COPY ... TO/FROM PROGRAM`. تقييد
حساب التشغيل العادي لصلاحيات DML بس على جداول التطبيق تحديداً (defense in depth) بيقلل
نطاق الضرر بشكل كبير حتى لو الطبقات التانية فشلت.

## 3. التوصية (لتطبيقها يدوياً، مش تلقائياً)

الخطوات دي **للتنفيذ اليدوي مستقبلاً بمعرفة صاحب المشروع**، مش سكريبت هيتشغّل تلقائياً:

```sql
-- 1. حساب مخصص للتطبيق وقت التشغيل (DML بس، بلا أي صلاحية DDL أو ملكية جداول)
CREATE ROLE app_runtime WITH LOGIN PASSWORD '...قيمة قوية عشوائية...';
GRANT CONNECT ON DATABASE alaa_eldin TO app_runtime;
GRANT USAGE ON SCHEMA public TO app_runtime;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO app_runtime;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO app_runtime;
-- لأي جدول جديد يتضاف بترحيل مستقبلي، الصلاحية الافتراضية دي بتتطبق تلقائياً:
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_runtime;
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT USAGE, SELECT ON SEQUENCES TO app_runtime;

-- 2. الحساب المالك الحالي (أو حساب جديد بنفس صلاحيات المالك) يفضل هو اللي بينفذ الترحيلات
--    فقط — يُستخدم في متغير بيئة منفصل (مثلاً MIGRATION_DATABASE_URL) بيتحط بس وقت خطوة
--    "npm run db:migrate"، ومش نفس القيمة اللي السيرفر شغّال بيها وقت خدمة الطلبات.
```

بعد التنفيذ اليدوي، التغيير المطلوب في الكود بسيط: `db.ts` (وملف الترحيل `migrate.ts` لو
منفصل) يقرأوا متغيرين مختلفين (`DATABASE_URL` للتشغيل العادي، ومتغير تاني للترحيل) بدل
متغير واحد مشترك — ده تغيير مستقبلي منفصل عن هذه المراجعة الأمنية، ومحتاج تنسيق فعلي مع
إعداد Railway (متغيرات بيئة جديدة + تأكد من نجاح الترحيل بالحساب الجديد قبل أي قطع
للحساب القديم).

## 4. ما لم يتم تنفيذه عمداً في هذه المراجعة

- لم يتم إنشاء أي حساب/دور جديد في قاعدة بيانات الإنتاج.
- لم يتم تغيير `DATABASE_URL` الحالي أو أي بيانات اعتماد.
- لم يتم تدوير (rotate) كلمة مرور قاعدة البيانات الحالية.
- لا يوجد دليل حالياً على أن هذا الفصل مطبّق فعلياً في بيئة الإنتاج — أي ادعاء بخلاف ذلك
  غير دقيق لحد ما يتحقق منه فعلياً بعد التنفيذ اليدوي.
