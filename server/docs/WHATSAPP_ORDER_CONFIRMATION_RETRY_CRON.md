# جدولة معالج إعادة محاولة تأكيد الطلب عبر واتساب (Railway Cron)

## ⚠️ تحديث ٢٠٢٦-٠٩-٢٥ — محاولة تفعيل فعلية، أوقفها حد Railway للخطة المجانية؛ تأجيل بقرار صاحب المشروع

تم إنشاء ثلاث خدمات Railway Cron حقيقية بنجاح في نفس الجلسة (انتهاء صلاحية الولاء،
تذكير السلة المهجورة، تنفيذ الأسعار المجدولة — راجع الملفات المقابلة). محاولة إنشاء
الخدمة الرابعة (خاصة بالملف ده) رجعت الخطأ التالي من Railway API صراحة:

> Free plan resource provision limit exceeded. Please upgrade to provision more resources!

يعني المشروع وصل لحد أقصى لعدد الخدمات المسموح بيه على الخطة المجانية الحالية (5 خدم:
Postgres + خدمة الويب + 3 Cron Jobs). **لازم ترقية خطة Railway** (أو حذف/دمج خدمة
موجودة) قبل ما تقدر تضيف الخدمة الرابعة دي فعلياً. الخطوات تحت لسه صحيحة 100% ومفيش
حاجة فيها تغيّرت — بس محتاجة مساحة إضافية على Railway الأول.

**قرار صاحب المشروع (٢٠٢٦-٠٩-٢٥)**: تأجيل ترقية الخطة حالياً — تم تقييم الأثر الفعلي
لعدم وجود الخدمة دي واتضح إنه محدود جداً: بيأثر بس على حالة نادرة جداً (فشل مؤقت قابل
لإعادة المحاولة `retryable` من Meta وقت إرسال تأكيد الطلب التلقائي أول مرة)، ومفيش أي
تأثير على الطلب نفسه أو الدفع أو المخزون. **البديل اليدوي موجود وشغّال فعلياً بدون هذه
الخدمة**: زرار "إعادة إرسال" في درج الطلب بلوحة التحكم بيغطي نفس الحالة — الأدمن بس
لازم يلاحظ ويضغط الزرار بدل ما يحصل تلقائياً كل 15-30 دقيقة. **الخطوات تحت لسه صحيحة
100%** لو حابب تفعّلها لاحقاً بعد ترقية الخطة.

---

هذا الملف توثيق وتوصية فقط — **مفيش جدولة (Railway Cron Job أو غيرها) اتضافت أو
اتفعّلت تلقائياً كجزء من هذا التغيير**. أمر `npm run whatsapp:retry-confirmations`
موجود وجاهز، لكنه مجرد سكريبت يدوي حتى يتم ربطه فعلياً بجدولة خارجية بمعرفة صاحب
المشروع.

## لماذا مفيش scheduler جوه التطبيق نفسه

نفس مبدأ `loyalty:expire` و`notify:abandoned-cart` بالظبط — راجع
[`LOYALTY_EXPIRY_CRON.md`](./LOYALTY_EXPIRY_CRON.md) لشرح كامل للمبدأ ده.

## إعداد Railway Cron Job (خطوات يدوية)

1. من لوحة تحكم Railway → المشروع → أضف خدمة جديدة من نوع "Cron Job" (منفصلة عن خدمة
   الويب الأساسية، بس بتشارك نفس الـ repo/environment variables زي `DATABASE_URL`
   ومتغيرات واتساب `WHATSAPP_ACCESS_TOKEN`/`WHATSAPP_PHONE_NUMBER_ID`/
   `WHATSAPP_ORDER_CONFIRMATION_TEMPLATE`).
2. Build command: نفس أمر بناء السيرفر الحالي (`npm install && npm run build --prefix server`).
3. Start command: `npm run whatsapp:retry-confirmations --prefix server`
4. **الجدولة**: التوصية **مرة كل 15-30 دقيقة**. الفشل المؤقت (شبكة/429/5xx من Meta)
   نادر عملياً، فمفيش داعي لتشغيل كل دقيقة؛ في نفس الوقت العميل ما ينفعش ينتظر ساعات
   لتأكيد طلبه لو حصل عطل مؤقت في المزوّد وقت إنشاء الطلب. مثال: `*/15 * * * *`.
5. `WHATSAPP_RETRY_BATCH_SIZE` (اختياري، افتراضي 20) — أقصى عدد إشعارات فاشلة تتعالج
   في تشغيلة واحدة، عشان تشغيلة واحدة ما تاخدش وقت طويل لو فيه عدد كبير من الفشل دفعة
   واحدة (مثال: انقطاع مؤقت طويل في اتصال Meta نفسه).

## أي فشل قابل لإعادة المحاولة تحديداً (ومش أي فشل)

كل فشل إرسال تلقائي بيتصنّف صراحة (`failure_class`، عمود مستقل في
`whatsapp_notification_deliveries`، راجع migration `0062`) لواحدة من ثلاث فئات:

- **`retryable`** — فشل مزوّد مؤقت مؤكد (Meta بترجع HTTP 429 أو 5xx صراحة). **الوحيدة**
  المؤهلة لإعادة محاولة تلقائية.
- **`permanent`** — أي رد HTTP آخر من Meta (توكن غلط، قالب غير موجود/غير معتمد، لغة أو
  بارامترات غلط، رقم وجهة غير صالح). إعادة محاولة تلقائية عليها **ممنوعة تماماً** —
  الخطأ مش هيتحل بإعادة المحاولة أصلاً.
- **`unknown`** — الطلب فشل قبل ما نستلم أي رد فعلي من Meta خالص (تايم آوت محلي أو
  انقطاع شبكة). **ممنوع تماماً** إعادة محاولة تلقائية عليها هي كمان — رغم إنها مش خطأ
  دائم في حد ذاتها. السبب: **Meta ممكن تكون استلمت الرسالة الأصلية فعلاً** قبل ما
  الخطأ المحلي يحصل، فإعادة محاولة تلقائية عليها ممكن تنتج **رسالة تأكيد مكررة فعلياً
  للعميل** — وتجنّب التكرار ده أهم من محاولة "التأكد" تلقائياً. الإشعار بيفضل `failed`
  بحالة `failure_class='unknown'` إلى أن يتدخّل الأدمن يدوياً (زر "إعادة الإرسال" في
  لوحة التحكم، اللي بيوضّح للأدمن إن الحالة "غير مؤكدة" مش "فشل قاطع").

السكريبت ده (`listRetryableFailedNotifications`) بيستبعد `permanent` و`unknown` من
استعلام المرشّحين نفسه — بس القاعدة الحقيقية والمُعتمَدة مفروضة كمان جوه الـ `UPDATE`
الذرّي نفسه في `claimAutomaticNotification`/`tryFailedRetryClaim`
(`WHERE ... AND failure_class = 'retryable' AND ...`)، مش بس في فلترة الاستعلام —
فحتى لو استُدعيت دالة الادّعاء مباشرة على إشعار `permanent` أو `unknown` بالغلط، النظام
هيرفض برضه (`reason: 'not_retryable'`) من غير أي اتصال بـ Meta. `attempt_count` كمان
لازم يكون لسه أقل من `MAX_AUTOMATIC_ATTEMPTS` (5). لو الإشعار `retryable` وصل لأقصى
عدد محاولات، بيفضل `failed` نهائياً وبيحتاج تدخّل يدوي من الأدمن (اللي بيتخطى نظام
الملكية دي بالكامل عمداً — راجع تعليق `sendOrderConfirmationWhatsApp`).

## الأمان تحت التداخل والتزامن (Overlapping Runs / Multi-Instance)

كل عنصر في الدفعة بيمر على **نفس** مسار `claimAutomaticNotification` الذرّي اللي
بيستخدمه أول محاولة إرسال تلقائي بالظبط — مفيش أي منطق منفصل أو "مختصر" هنا. يعني:

- تشغيلة يدوية فوق تشغيلة Railway cron جارية، أو تشغيلتين cron متداخلتين (تأخير في
  تشغيلة سابقة)، آمنتين تماماً من غير أي تنسيق إضافي في كود السكريبت نفسه — الضمان
  كله جوه PostgreSQL (`UPDATE ... WHERE status='failed' AND attempt_count < ...`
  ذرّية، راجع `whatsappNotificationDeliveryService.ts`).
- لو عملية تانية (مثلاً نسخة سيرفر Railway تانية بتعالج نفس الطلب من مسار مختلف)
  ادّعت الملكية في نفس اللحظة، الطرف الخاسر بيرجع `active_owner` من غير أي إرسال Meta
  فعلي مكرر.

## التحقق من إن المعالج شغّال صح فعلاً

السكريبت بيطبع سطر واحد واضح زي:
```
whatsapp order-confirmation retry: attempted 3, sent 2, still failed 1
```

## الحالة الحالية

- **الكود جاهز (CODE READY)**: السكريبت مبني، بيطلع exit code صفر عند النجاح وواحد
  عند الفشل، بدون أي unhandled promise rejection.
- **Railway Cron: غير مُفعّل (NOT CONFIGURED)** — نفس التحقق اللي تم في
  `LOYALTY_EXPIRY_CRON.md`/`ABANDONED_CART_CRON.md`: قائمة خدمات مشروع Railway
  الفعلية بها خدمتين بس (قاعدة البيانات وخدمة الويب الأساسية)، **لا توجد أي خدمة من
  نوع Cron Job**. أي ادعاء بأن إعادة المحاولة التلقائية "شغّالة فعلياً في الإنتاج"
  غير صحيح حالياً حتى يتم إعداد الخدمة دي فعلياً من صاحب المشروع.
