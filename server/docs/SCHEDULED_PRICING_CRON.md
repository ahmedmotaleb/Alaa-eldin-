# جدولة معالج تنفيذ الأسعار المستقبلية (Railway Cron)

## ✅ تحديث ٢٠٢٦-٠٩-٢٥ — تم التفعيل فعلياً، وتم التحقق من تشغيلها الحقيقي

خدمة Railway Cron حقيقية اتعملت واتأكدت (`cron-scheduled-pricing`، جدولة `*/15 * * * *`
UTC، `restartPolicyType: NEVER`، `DATABASE_URL` مربوطة بمرجع مباشر لخدمة Postgres).
**تم التحقق من التشغيل الفعلي نفسه** (مش بس نجاح الـ deploy) عبر لوج الخدمة الحقيقي —
الخدمة اشتغلت فعلياً كل 15 دقيقة بالظبط منذ التفعيل، وطبعت السطر المتوقع في كل مرة:
`scheduled pricing: applied 0, conflicts 0, across 1 batch(es)` (٠ تطبيق متوقع تماماً —
لسه مفيش أي أدمن جدول تغيير سعر مستقبلي فعلياً).

باقي الملف تحت (بما فيه قسم "الحالة الحالية" في الآخر) بيوثّق الحالة **قبل** هذا
التحديث — سايبينه لغرض التتبّع التاريخي، مش لأنه لسه يعكس الواقع.

---

هذا الملف توثيق وتوصية فقط — **مفيش جدولة (Railway Cron Job أو غيرها) اتضافت أو
اتفعّلت تلقائياً كجزء من هذا التغيير**. أمر `npm run pricing:apply-scheduled` موجود
وجاهز، لكنه مجرد سكريبت يدوي حتى يتم ربطه فعلياً بجدولة خارجية بمعرفة صاحب المشروع.

راجع كمان [`LOYALTY_EXPIRY_CRON.md`](./LOYALTY_EXPIRY_CRON.md) و
[`ABANDONED_CART_CRON.md`](./ABANDONED_CART_CRON.md) لنفس التوثيق الخاص بالمعالجات
الدورية الأخرى — نفس المبدأ بالضبط.

## لماذا مفيش scheduler جوه التطبيق نفسه

نفس مبدأ كل المعالجات الدورية الموجودة بالفعل: عملية السيرفر (Express) مسؤوليتها خدمة
الطلبات بس — تنفيذ الأسعار المجدولة بيُشغَّل كسكريبت مستقل تماماً، بمعرفة جدولة خارجية
(Railway Cron Job). هنا الأمر أهم من العادي: جدولة سعر **مقصودة بتوقيت محدد** (زي عرض
يبدأ الساعة معيّنة) — تأخير تنفيذها لازم يكون بحد أقصى معروف (تكرار الجدولة)، مش معتمد
على حد يفتح لوحة التحكم يدوياً.

## إعداد Railway Cron Job (خطوات يدوية)

1. من لوحة تحكم Railway → المشروع → أضف خدمة جديدة من نوع "Cron Job".
2. Build command: نفس أمر بناء السيرفر الحالي.
3. Start command: `npm run pricing:apply-scheduled --prefix server`
4. متغيرات البيئة المطلوبة: `DATABASE_URL` فقط.
5. **الجدولة الموصى بها: كل 15 دقيقة (`*/15 * * * *`)** — على عكس انتهاء صلاحية
   الولاء أو تذكير السلة (مرة واحدة يومياً كافية)، جدولة السعر مرتبطة بلحظة زمنية
   محددها الأدمن (`starts_at`)، فتأخير التنفيذ يعني إن السعر الجديد ما يبدأش فعلياً
   في الميعاد المطلوب. كل 15 دقيقة يوازن بين الدقة الزمنية المعقولة وعدد مرات التشغيل.

## فحص التعارض (Conflict Detection)

كل جدولة بتسجّل السعر الفعلي وقت الإنشاء (`expected_current_price`). لو حد عدّل السعر
يدوياً (أو عبر تسعير جماعي) بعد إنشاء الجدولة وقبل تنفيذها، التنفيذ **يرفض** يطبّق
ويسجّل حالة الجدولة كـ `conflict` بدل ما يبني فوق افتراض قديم صامت أو يفقد التعديل
اليدوي الأحدث. الأدمن لازم يراجع الجدولات اللي حالتها `conflict` ويقرر يدوياً (يلغيها
أو يعمل جدولة جديدة بالسعر الفعلي الحالي).

## الأمان تحت التداخل (Overlapping Runs)

`runApplyScheduledBatch` بيستخدم `SELECT ... FOR UPDATE SKIP LOCKED` على مستوى قاعدة
البيانات — نفس مبدأ باقي المعالجات الدورية بالضبط. تشغيلتين متزامنتين ما يقدروش
ينفذوا نفس الجدولة مرتين.

## التحقق من إن المعالج شغّال صح فعلاً

بعد الربط بالجدولة، راقب لوجات خدمة الـ Cron — السكريبت بيطبع سطر واحد واضح زي:

```
scheduled pricing: applied 3, conflicts 0, across 1 batch(es)
```

## الحالة الحالية (تم التحقق منها فعلياً عبر Railway API وقت كتابة هذا الملف)

- **الكود جاهز (CODE READY)**: السكريبت مبني بنفس نمط أدوات الكرون الموجودة (بدون
  Express، بدون setInterval، exit code واضح، محدود العدد `MAX_BATCHES`).
- **Railway Cron: غير مُفعّل (NOT CONFIGURED)** — تم التأكد فعلياً عبر
  `mcp__Railway__list-services` على مشروع `bb9f5517-0a26-4320-9796-9735666fe6f9`:
  خدمتان بس (`Postgres`، `Alaa-eldin-`). **لا توجد أي خدمة من نوع Cron Job** — لو
  أدمن أنشأ جدولة سعر مستقبلية، مفيش حالياً أي حاجة هتنفّذها تلقائياً في الإنتاج لحد
  ما يتضاف Cron Job فعلياً بالخطوات فوق.
