# جدولة معالج تذكير السلة المهجورة (Railway Cron)

## ✅ تحديث ٢٠٢٦-٠٩-٢٥ — تم التفعيل فعلياً

خدمة Railway Cron حقيقية اتعملت واتأكدت (`cron-abandoned-cart`، جدولة `0 */6 * * *` UTC،
`restartPolicyType: NEVER`). المتغيرات مربوطة بمرجع مباشر: `DATABASE_URL` من خدمة
Postgres، و`VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY`/`VAPID_SUBJECT` من خدمة الويب
الأساسية — يعني الإشعارات الفعلية (Web Push) هتتبعت من أول تشغيلة، مش بس السكريبت
شغّال بدون إشعار حقيقي. تم التحقق من نجاح أول build/deploy فعلياً عبر Railway API
(`environment-status` بيرجع `state: cronReady`).

باقي الملف تحت (بما فيه قسم "الحالة الحالية" في الآخر) بيوثّق الحالة **قبل** هذا
التحديث — سايبينه لغرض التتبّع التاريخي، مش لأنه لسه يعكس الواقع.

---

هذا الملف توثيق وتوصية فقط — **مفيش جدولة (Railway Cron Job أو غيرها) اتضافت أو
اتفعّلت تلقائياً كجزء من هذا التغيير**. أمر `npm run notify:abandoned-cart` موجود
وجاهز، لكنه مجرد سكريبت يدوي حتى يتم ربطه فعلياً بجدولة خارجية بمعرفة صاحب المشروع.

## لماذا مفيش scheduler جوه التطبيق نفسه

نفس مبدأ `loyalty:expire` و`db:cleanup` بالظبط — راجع
[`LOYALTY_EXPIRY_CRON.md`](./LOYALTY_EXPIRY_CRON.md) لشرح كامل للمبدأ ده.

## إعداد Railway Cron Job (خطوات يدوية)

1. من لوحة تحكم Railway → المشروع → أضف خدمة جديدة من نوع "Cron Job" (منفصلة عن خدمة
   الويب الأساسية، بس بتشارك نفس الـ repo/environment variables زي `DATABASE_URL`).
2. Build command: نفس أمر بناء السيرفر الحالي (`npm install && npm run build --prefix server`).
3. Start command: `npm run notify:abandoned-cart --prefix server`
4. متغيرات البيئة المطلوبة: `DATABASE_URL` (نفس قيمة خدمة الويب)، بالإضافة لمتغيرات
   Web Push (`VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY`) لو عايز الإشعارات الفعلية تتبعت —
   لو دول مش مُعدّين، السكريبت هيكمل من غير كسر (`sendPushToUser` بترجع بصمت لو
   الاشتراك أو الإعداد غير متاح)، بس مفيش أي إشعار فعلي هيوصل للعميل.
5. **الجدولة**: السلوك مبني على نافذة ثابتة 24 ساعة (`ABANDONED_CART_HOURS` في
   `abandonedCartService.ts`) — يعني سلة اتسابت من غير تحديث لأكتر من 24 ساعة بس هي
   المؤهلة للتذكير. التوصية: **مرة كل 4-6 ساعات** (مثلاً `0 */6 * * *` بتوقيت UTC) —
   كافية لالتقاط السلات اللي عدّت الـ 24 ساعة بدون تأخير طويل، ومن غير الحاجة لتشغيل
   كل ساعة (النافذة نفسها 24 ساعة، فمفيش فايدة من تكرار أعلى بكتير من كده).
   لا يوجد هنا حساسية توقيت محلي (زي حالة "3 صباحاً بتوقيت القاهرة" في معالج انتهاء
   الولاء) — الجدولة هنا بمعدل تكرار بسيط، مش وقت محدد في اليوم، فمفيش داعي لتحويل
   منطقة زمنية.

## عدم تكرار التذكيرات (مطلوب صراحة)

`cart_snapshots.reminder_sent_at` هو آلية منع التكرار: بمجرد إرسال تذكير لسلة معيّنة،
العمود ده بيتحدّث فوراً ومفيش تذكير تاني هيتبعت لنفس السلة إلا لو العميل عدّل سلته
تاني (وقتها `upsertCartSnapshot` بيصفّر العمود ده تلقائياً — تغيير حقيقي في السلة يعني
"لسه شغّال عليها"، مش مهجورة).

## الأمان تحت التداخل (Overlapping Runs)

**تم اكتشاف وإصلاح ثغرة تكرار محتملة في هذه الدفعة**: النسخة الأصلية من
`sendAbandonedCartReminders` كانت بتفحص `reminder_sent_at IS NULL` كـ `SELECT` منفصل
عن `UPDATE` إرسال التذكير — لو تشغيلتين اشتغلوا في نفس الوقت بالخطأ (تشغيلة يدوية
زيادة، أو تأخير في تشغيلة سابقة)، الاتنين كانوا ممكن يشوفوا نفس السلة مؤهلة ويبعتوا
تذكير مكرر لنفس العميل قبل ما أي حد يحدّث العمود.

**الإصلاح**: كل صف دلوقتي بيتم "حجزه" ذرّياً عن طريق:
```sql
UPDATE cart_snapshots SET reminder_sent_at = now() WHERE user_id = $1 AND reminder_sent_at IS NULL
```
الشرط `reminder_sent_at IS NULL` جوه نفس جملة الـ `UPDATE` (مش `SELECT` منفصل) بيخلي
العملية ذرّية على مستوى قاعدة البيانات — لو تشغيلتين حاولوا يحجزوا نفس الصف في نفس
اللحظة، Postgres بيضمن إن واحدة بس تنجح (`rowCount = 1`) والتانية ترجع صفر صفوف
(`rowCount = 0`) فتتجاهل الصف ده تماماً. لو العميل مش مؤهل فعلياً لإشعار (تفضيلاته
معطّلة)، الحجز بيتلغى (`reminder_sent_at` يرجع `NULL`) عشان تشغيلة قادمة تقدر تعيد
الفحص لو تفضيلاته اتغيّرت. تم إضافة اختبار مخصص (`abandonedCartService.test.ts` —
"sends the reminder exactly once even when two runs process the same candidate
concurrently") بيشغّل تشغيلتين متزامنتين فعلياً على نفس المرشّح ويتأكد إن الإشعار
بيتبعت مرة واحدة بالظبط.

## التحقق من إن المعالج شغّال صح فعلاً

السكريبت بيطبع سطر واحد واضح زي:
```
sent 3 abandoned-cart reminder(s), 1 skipped (already converted), 2 skipped (promotions disabled)
```

## الحالة الحالية (تم التحقق منها فعلياً عبر Railway API)

- **الكود جاهز (CODE READY)**: السكريبت مبني، بيطلع exit code صفر عند النجاح وواحد عند
  الفشل، بدون أي unhandled promise rejection. تم تشغيله يدوياً محلياً والتأكد من ناتجه،
  وتم إضافة اختبار تلقائي صريح على الأمان تحت التداخل.
- **Railway Cron: غير مُفعّل (NOT CONFIGURED)** — نفس التحقق اللي تم في
  `LOYALTY_EXPIRY_CRON.md`: قائمة خدمات مشروع Railway الفعلية بها خدمتين بس (قاعدة
  البيانات وخدمة الويب الأساسية)، **لا توجد أي خدمة من نوع Cron Job**. أي ادعاء بأن
  تذكيرات السلة المهجورة "شغّالة تلقائياً في الإنتاج" غير صحيح حالياً.
