# علاء الدين — سوبر ماركت عربي PWA

تطبيق Mobile-first باللغة العربية فقط، يدعم RTL، كتالوج منتجات، أقسام، فرز، صفحة منتج، سلة، حد أدنى للطلب، شحن مجاني بعد حد معين، تسجيل دخول حقيقي بالبريد الإلكتروني (اختياري، مش شرط للطلب)، Checkout بالدفع عند الاستلام يدعم الزوار والمسجّلين، وإرسال الطلب عبر واتساب.

المشروع مكوّن من ثلاثة أجزاء:

- الواجهة (هذا المجلد): تطبيق العميل، React + Vite.
- الخادم (`server/`): Node.js + Express + PostgreSQL — حسابات المستخدمين والطلبات فعلاً محفوظة على السيرفر، مش localStorage.
- لوحة تحكم صاحب المتجر (`admin/`): تطبيق React + Vite منفصل، لإدارة كل جوانب المتجر (طلبات، منتجات، عملاء، خصومات، تحليلات، محفظة، تسويق، إعدادات) — راجع قسم "لوحة التحكم" بالأسفل للتفاصيل الكاملة.

## التشغيل (تطوير)

يحتاج المشروع قاعدة بيانات PostgreSQL شغّالة قبل تشغيل الخادم — محلياً (`postgresql` مثبت ومُشغَّل) أو أي استضافة PostgreSQL جاهزة:

```bash
# تشغيل PostgreSQL محلياً (Ubuntu/Debian) وإنشاء قاعدة البيانات مرة واحدة فقط
sudo service postgresql start
sudo -u postgres createdb alaa_eldin
sudo -u postgres psql -c "ALTER USER postgres PASSWORD 'postgres';"

npm install
cd server && npm install && cd ..
cd admin && npm install && cd ..
npm run dev
```

هذا الأمر يشغّل الواجهة (Vite على `5173`)، الخادم (`8787`)، ولوحة التحكم (Vite على `5174`) في نفس الوقت. كل واجهة بتوجّه طلبات `/api` للخادم تلقائياً أثناء التطوير (`vite.config.ts` في كل مجلد).

ثم افتح العنوان الذي يظهر في الطرفية (`http://localhost:5173` للعميل، `http://localhost:5174/admin/` للوحة التحكم).

## بناء نسخة الإنتاج والتشغيل

```bash
npm run build          # واجهة العميل -> dist/
npm run build:server   # الخادم -> server/dist/
npm run build:admin    # لوحة التحكم -> admin/dist/
npm run start          # يشغّل خادم Express واحد يخدم كل شيء (العميل + /admin + /api) على نفس المنفذ
```

في وضع الإنتاج (`NODE_ENV=production`) الخادم نفسه يقدّم ملفات `dist/` (تطبيق العميل على `/`) و`admin/dist/` (لوحة التحكم على `/admin`) بالإضافة إلى `/api`، فلا حاجة لإعداد CORS أو منافذ منفصلة. `npm run start` يستخدم حزمة `cross-env` لضبط `NODE_ENV` — بيشتغل على PowerShell/cmd.exe وليس على Bash/zsh بس (الصيغة القديمة `NODE_ENV=production node ...` مباشرة كانت بتفشل على PowerShell).

قاعدة البيانات PostgreSQL — الاتصال عبر متغيّر البيئة `DATABASE_URL` (افتراضياً `postgresql://postgres:postgres@localhost:5432/alaa_eldin` لو مش موجود). الجداول تُنشأ تلقائياً عند أول تشغيل للخادم (`server/src/db.ts`, دالة `initDb()`)، والبذرة الأولى (الأقسام/المنتجات/بانر افتراضي/إعدادات المتجر) تُزرع تلقائياً لو الجداول فاضية — لا حاجة لأي هجرة (migration) يدوية.

## النشر على Railway (Deploy تلقائي مع كل push على GitHub)

المشروع فيه `railway.json` جاهز في الجذر — بمجرد ربط الحساب، Railway بيبني وبيشغّل المشروع صح من غير أي إعداد إضافي. الخطوات (مرة واحدة، من لوحة Railway نفسها):

1. **New Project → Deploy from GitHub repo** → اختار الريبو `ahmedmotaleb/Alaa-eldin-`.
2. **أضف قاعدة بيانات**: من نفس المشروع، **+ New → Database → Add PostgreSQL** — Railway بينشئ قاعدة بيانات ويوفّر متغيّر `DATABASE_URL` تلقائياً.
3. **اربط المتغيّر بالخدمة**: في إعدادات خدمة الويب (مش قاعدة البيانات) → **Variables** → أضف `DATABASE_URL` واختار الـ reference بتاع قاعدة البيانات اللي عملتها (Railway بيقترحها تلقائياً، غالباً باسم `${{Postgres.DATABASE_URL}}`).
4. مفيش حاجة تانية تتظبط — `railway.json` فيه أوامر البناء (`npm install` + `build` لكل الثلاث أجزاء) وأمر التشغيل (`npm run start`) جاهزين، و`PORT` بيتقرأ تلقائياً من `process.env.PORT` اللي Railway بيوفّره.
5. بعد أول Deploy ناجح، أي `git push` على فرع `main` هيعمل Deploy جديد تلقائياً من غير أي خطوة يدوية.

بعد أول Deploy، سجّل حساب عميل عادي من التطبيق المنشور، وبعدين رقّيه لمدير عبر تشغيل `make-admin` محلياً وأنت متصل بنفس `DATABASE_URL` (أو مؤقتاً من Railway's شل عبر **Settings → Deploy Logs → Shell** لو متاحة في خطتك).

## أهم الإعدادات

اسم المتجر، رقم واتساب، العملة، الحد الأدنى للطلب، حد الشحن المجاني، وتكلفة التوصيل — كل ده أصبح محفوظاً في قاعدة البيانات (جدول `store_settings`، صف واحد ثابت) وليس ملف كود. التعديل الفعلي من لوحة التحكم:

- `/settings/store` — اسم المتجر، رقم واتساب، رمز العملة
- `/settings/delivery` — الحد الأدنى للطلب، حد الشحن المجاني، تكلفة التوصيل

تطبيق العميل يجيب هذه القيم مرة واحدة عند فتح التطبيق (`GET /api/settings`، ضمن نفس التحميل الأولي للكتالوج عبر `CatalogContext`) ويستخدمها في كل مكان بدل الاستيراد الثابت القديم — أي تعديل من لوحة التحكم يظهر للعميل من أول فتح جديد للتطبيق.

رقم واتساب يجب أن يكون بصيغة دولية بدون علامة +، مثال مصر:

## اللغة

التطبيق عربي بالكامل (RTL، `lang="ar"`، `dir="rtl"`) ولا توجد واجهة إنجليزية للعميل. كل النصوص الظاهرة للعميل مركزية في `src/i18n/ar.ts` بدل تكرارها داخل الصفحات — أي نص جديد يظهر للعميل يجب إضافته هناك أولاً. الهيكل يسمح بإضافة لغة أخرى لاحقاً دون المساس بتجربة العربية الحالية، لكن لا يوجد حالياً أي مبدّل لغة ولا يظهر أي نص إنجليزي كـ fallback. أخطاء الـ API ترجع من الخادم كأكواد إنجليزية داخلية (مثل `invalid_credentials`) وتُترجم على الواجهة عبر `ar.errors.forCode()` — لا يظهر أي كود أو نص تقني للعميل.

## الحسابات وتسجيل الدخول

- تسجيل الدخول بالبريد الإلكتروني وكلمة المرور فقط (لا يوجد رقم هاتف/OTP، يحتاج مزوّد SMS خارجي).
- الجلسات حقيقية من السيرفر: عند تسجيل الدخول يُنشأ سطر في جدول `sessions` ويُرسل token في كوكي `httpOnly`، وتسجيل الخروج يمسح الجلسة فعلياً من قاعدة البيانات (وليس فقط من المتصفح).
- كلمات المرور مشفّرة بـ bcrypt، لا تُخزَّن أبداً كنص صريح.
- **"نسيت كلمة المرور؟"** موجودة فعلياً (`/forgot-password` في تطبيق العميل، ورابط مماثل في صفحة تسجيل دخول لوحة التحكم يوديك لنفس الصفحة — نفس نظام الحسابات). تعمل عبر [Resend](https://resend.com):
  - `POST /api/auth/forgot-password` يقبل `{email}` ويرجع نفس الرد (`204`) سواء كان الإيميل مسجّل أو لأ (منعاً لكشف إيميلات عملاء حقيقيين). لو الإيميل مسجّل فعلاً، يتولّد رمز عشوائي في جدول `password_resets` (صالح لمدة ساعة، رمز واحد فعّال بحد أقصى لكل مستخدم) ويتبعت بريد فيه رابط `PUBLIC_APP_URL/reset-password?token=...`.
  - `POST /api/auth/reset-password` يقبل `{token, password}`، يتحقق من الرمز وصلاحيته، يحدّث `password_hash`، ويمسح كل جلسات المستخدم القديمة (`sessions`) كإجراء أمان.
  - **متغيرات بيئة مطلوبة للتشغيل الفعلي** (Railway → Variables على خدمة التطبيق):
    - `RESEND_API_KEY` — من حساب [resend.com](https://resend.com) (فيه باقة مجانية). **بدونها**، السيرفر لسه يشتغل عادي لكن بيكتفي بطباعة رابط الاستعادة في الـ logs بدل ما يبعت بريد فعلي (مفيد للتطوير المحلي).
    - `RESEND_FROM` — عنوان المرسل، افتراضياً `علاء الدين <onboarding@resend.dev>`. **ملحوظة مهمة**: `onboarding@resend.dev` (سندر Resend التجريبي بدون توثيق دومين) بيقبل الإرسال بس للإيميل المرتبط بحساب Resend نفسه — لإرسال حقيقي لكل العملاء لازم توثّق دومين خاص بيك في Resend وتحط عنوان مرسل عليه هنا (مثلاً `علاء الدين <noreply@yourdomain.com>`).
    - `PUBLIC_APP_URL` — رابط تطبيق العميل العام (مثلاً `https://alaa-eldin-production.up.railway.app`) عشان رابط الاستعادة في البريد يشتغل صح. افتراضياً `http://localhost:5173` (مناسب للتطوير المحلي فقط).
- السلة تبقى محلية (`localStorage`) حتى إتمام الطلب لا تتطلب تسجيل دخول للتصفح والإضافة للسلة.
- **تسجيل الدخول اختياري تماماً عند إتمام الطلب.** `/checkout` لا يفرض تسجيل الدخول: يقدر أي زائر يكمل طلبه بالاسم/الموبايل/العنوان بدون حساب. لو المستخدم مسجّل دخوله فعلاً، الطلب يترتبط تلقائياً بحسابه (`user_id`)؛ لو زائر، يتسجّل الطلب بدون حساب (`user_id = NULL`) لكنه يظهر بشكل طبيعي في لوحة التحكم (الطلبات، التحليلات، المحفظة) مع توضيح "طلب زائر بدون حساب" بدل البريد الإلكتروني.
- صفحة التأكيد (`/confirmation/:orderId`) تعرض تفاصيل الطلب من رد إنشاء الطلب مباشرة (بدون أي طلب API إضافي) — فمفيش endpoint عام يسمح بمعرفة تفاصيل طلب حد تاني لو حد لقط رقم الطلب. لو الزائر عمل تحديث للصفحة (refresh) أو رجعلها لاحقاً بدون تسجيل دخول، بيشوف رسالة توضح إن تفاصيل الطلب متاحة بس مباشرة بعد إتمامه.
- تتبع الطلب (`/track/:id`) ما زال يتطلب تسجيل دخول عمداً — مفيش طريقة آمنة تسمح لزائر بمتابعة طلب لاحقاً بدون حساب من غير ما يكشف بيانات عملاء تانيين، فزر "تتبع الطلب" مش بيظهر في صفحة التأكيد للزوار أصلاً.
- الطلبات وحالتها (`/orders`, `/track/:id`) للمستخدمين المسجّلين محفوظة على السيرفر مرتبطة بالحساب، تظهر على أي جهاز يسجّل عليه نفس المستخدم دخوله.
- نموذج حالة الطلب 5 مراحل: قيد المراجعة، جاري التجهيز، **جاهز للتوصيل**، خرج للتوصيل، تم التسليم (+ إلغاء). تظهر في `/track/:id` وفي لوحة التحكم بنفس الترتيب.

## المنتجات والأقسام

المنتجات والأقسام محفوظة فعلياً في قاعدة البيانات (جدولا `categories` و`products` في `server/src/db.ts`)، وليست ملفات ثابتة. عند أول تشغيل تُزرع تلقائياً من `server/src/seedData.ts` إذا كانت الجداول فارغة. الواجهة تجلبها عبر `GET /api/categories` و`GET /api/products` وتوزّعها على كل الصفحات من خلال `CatalogContext` (`src/store/CatalogContext.tsx`) — لا يوجد استيراد مباشر لبيانات منتجات ثابتة في أي صفحة.

المنتجات تُعرض حالياً بإيموجي على خلفية ملوّنة (بدل صور حقيقية). لإضافة صور حقيقية لاحقاً، حدّث `ProductArt` في `src/components/ProductArt.tsx` ليعرض `<img>` بدل الإيموجي عند توفر مسار صورة للمنتج.

التعديل على المنتجات والأقسام (إضافة/تعديل سعر أو مخزون/إلخ) يتم فعلياً من لوحة التحكم — راجع قسم "لوحة التحكم" بالأسفل.

## المسارات

- `/onboarding` شاشة الترحيب الأولى (تظهر مرة واحدة فقط)
- `/` الرئيسية
- `/categories` كل الأقسام
- `/category/:categoryId` منتجات القسم (فرز + حالة تحميل)
- `/offers` عروض اليوم
- `/best-sellers` الأكثر مبيعاً
- `/product/:slug` صفحة المنتج
- `/search` البحث (عمليات بحث سابقة + الأكثر بحثاً + نتائج)
- `/cart` السلة (يشمل تطبيق كود خصم)
- `/login`, `/register` تسجيل الدخول / إنشاء حساب
- `/checkout` إتمام الطلب (تسجيل الدخول اختياري — يعمل كزائر أو كمستخدم مسجّل)
- `/confirmation/:orderId` تأكيد الطلب
- `/track/:orderId` تتبع الطلب (يعرض الحالة الحقيقية للطلب من قاعدة البيانات، ويحدّثها تلقائياً كل ١٥ ثانية — القيمة الوحيدة اللي بتغيّرها هي لوحة التحكم)
- `/orders` طلباتي (كل الطلبات السابقة، من شريط التنقل السفلي مباشرة)
- `/account` حسابي (بياناتك، تسجيل الخروج، وروابط التواصل والإعدادات)

## ملاحظات

- السلة محفوظة محلياً في `localStorage` (`alaa-eldin-cart`) فقط — الحسابات والطلبات على السيرفر.
- تتبع الطلب للقراءة فقط من طرف العميل — الحالة تتغيّر فقط من لوحة التحكم (`PATCH /api/admin/orders/:id/status`، يتطلب `is_admin`). كان فيه سابقاً endpoint عام `PATCH /api/orders/:id/status` يسمح لأي عميل مسجّل يغيّر حالة طلبه الخاص لأي قيمة (بما فيها "تم التسليم") من غير أي صلاحية إدارية — ده كان ثغرة حقيقية تكسر مصداقية بيانات "المحفظة" (التحصيل المحسوب من حالة "تم التسليم")، فاتشالت نهائياً.
- الدفع عند الاستلام فقط.
- إرسال واتساب يتم من جهاز العميل باستخدام `wa.me`.
- يجب وضع رقم واتساب الحقيقي قبل النشر.
- تكلفة التوصيل الافتراضية 30 ج.م لأن السعر العادي لم يتم تحديده في المتطلبات.
- أيقونات PWA حقيقية (`public/images/icon-192.png`, `icon-512.png`, `apple-touch-icon.png`, `favicon-32.png`) مولّدة من نفس تصميم `app-icon.svg` — قبل كده كان فيه أيقونة SVG واحدة بس في الـ manifest (`sizes: any`)، ومفيش `apple-touch-icon` ولا favicon في `index.html` أصلاً، فـ iOS Safari كان هيلتقط لقطة شاشة عشوائية كأيقونة عند "إضافة للشاشة الرئيسية" بدل شعار المتجر. لوحة التحكم (`admin/`) اتضاف لها نفس الـ favicon (SVG + PNG) لكن بدون باقي أيقونات الـ PWA لأنها مش تطبيق قابل للتثبيت أصلاً (دي تحديداً أداة إدارة من المتصفح).
- **مهم — service worker تطبيق العميل وصفحة `/admin`**: تطبيق العميل PWA (`vite-plugin-pwa`) وسيرفره على نفس الدومين اللي عليه `/admin`. الإعداد الافتراضي لـ `generateSW` كان بيسجّل `NavigationRoute` بدون أي denylist — أي إن أي متصفح زار تطبيق العميل ولو مرة واحدة (فعّل الـ service worker)، أي تنقّل تالي لـ `/admin` في نفس المتصفح كان بيترد عليه الـ service worker محلياً بصفحة تطبيق العميل نفسها (وبيظهر "الصفحة غير موجودة" من راوتر العميل) **من غير ما الطلب يوصل للسيرفر أصلاً** — وده سبب حقيقي شفناه فعلياً (لوحة التحكم بتفتح صفحة عميل بدل تسجيل الدخول، وسجلات الطلبات على Railway بتوضح صفر طلبات لـ `/admin`). الحل في `vite.config.ts`: `workbox.navigateFallbackDenylist: [/^\/admin/, /^\/api/]` — بيمنع الـ service worker من اعتراض أي تنقّل لمسارات `/admin` أو `/api`. أي متصفح فعّل الـ service worker القديم قبل هذا التعديل هيحتاج يزور تطبيق العميل تاني مرة واحدة (تحديث الـ service worker تلقائي بفضل `registerType: 'autoUpdate'`) قبل ما يقدر يفتح `/admin` بشكل طبيعي.

## أكواد الخصم

- كود الخصم يُدخل في صفحة `/cart`، ويتحقق منه السيرفر فعلياً عبر `POST /api/discounts/validate` (نوع الكود: نسبة مئوية أو قيمة ثابتة، حد أدنى للطلب، حد أقصى لعدد مرات الاستخدام، تاريخ انتهاء اختياري).
- التحقق يتكرر تلقائياً كلما تغيّر إجمالي السلة (تغيير كمية أو حذف منتج) — لو صار الكود غير صالح (مثلاً الطلب لم يعد يحقق الحد الأدنى) يُلغى بصمت من السلة.
- عند إتمام الطلب، السيرفر يعيد التحقق من الكود بنفسه (`POST /api/orders` مع `discountCode`) ولا يثق بأي قيمة خصم يرسلها المتصفح — يحسب قيمة الخصم بنفسه ويزيد عداد الاستخدام في نفس معاملة إنشاء الطلب.
- قيمة الخصم وكوده يُحفظان مع الطلب (`discount_code`, `discount_amount`) ويظهران في تأكيد الطلب، رسالة واتساب، وتفاصيل الطلب في لوحة التحكم.

## لوحة التحكم (`admin/`)

مبنية على نفس حسابات المستخدمين والخادم، بعمود `is_admin` في جدول `users`. لترقية حساب (لازم يكون مسجَّل بالفعل كعميل عادي أولاً) لصلاحية مدير:

```bash
npm run make-admin --prefix server -- email@example.com
```

**المبني فعلياً ومتصل ببيانات حقيقية:**
- تسجيل الدخول (نفس حسابات العملاء، لكن يرفض من ليس `is_admin`).
- **الرئيسية**: مبيعات اليوم، عدد الطلبات، متوسط الطلب، طلبات جديدة، رسم مبيعات ٧ أيام، أحدث ٥ طلبات، أكثر المنتجات مبيعاً — كل ده محسوب من الطلبات الحقيقية في قاعدة البيانات.
- **الطلبات**: كل التبويبات (جميع الطلبات، الجديدة، جاري التجهيز، **جاهزة للتوصيل**، خرجت للتوصيل، مكتملة، ملغاة) + بحث + لوحة تفاصيل الطلب (Drawer) + تغيير الحالة فعلياً عبر `PATCH /api/admin/orders/:id/status`.
- **المنتجات**: جدول كل المنتجات (بحث + فرز حسب القسم) مع إحصائيات (عدد المنتجات، المعروض، تحت حد التنبيه، متوسط الهامش)، إضافة منتج جديد، وتعديل منتج موجود (السعر، سعر ما قبل الخصم، التكلفة، الوحدة، الحالة، المخزون، حد التنبيه، الباركود، العلامة التجارية...) عبر `/api/admin/products`. حالة "عرض" تُحسب تلقائياً من وجود سعر قبل الخصم، وليست مفتاح تبديل يدوي.
- **الأقسام**: عرض كل الأقسام مع عدد منتجات كل قسم، وإضافة قسم جديد (id, اسم, إيموجي, لون) عبر `/api/admin/categories`.
- **المخزون**: جدول كل المنتجات مرتب حسب الأقرب لحد التنبيه، مع إحصائيات (قيمة المخزون بالتكلفة/بالبيع، عدد المنتجات تحت الحد، عدد المنتجات النافدة).
- **تحويلات المخزون** (`/products/moves`): سجل تاريخي حقيقي لكل حركة مخزون (جدول `stock_movements` منفصل) — إضافة/مرتجع/تلف/فقد/تعديل يدوي، مع تحديث رقم المخزون على المنتج فعلياً في نفس المعاملة. أي تعديل مباشر لرقم المخزون من صفحة تعديل منتج (`/products/edit/:id`) يُسجَّل تلقائياً كحركة "تعديل يدوي" في نفس السجل — مفيش طريقة لتغيير المخزون من غير ما تُسجَّل حركة.
- **العملاء**: جدول كل الحسابات غير الإدارية (بحث بالاسم/البريد/الهاتف) مع إحصائيات (عدد العملاء، عملاء جدد آخر ٧ أيام، متوسط قيمة الطلب، عدد من لم يطلبوا بعد)، وصفحة ملف عميل واحد (`/customers/:id`) تعرض بياناته وسجل كل طلباته — كل ده محسوب من جدولي `users`/`orders` الحقيقيين عبر `/api/admin/customers`. عدد الطلبات وإجمالي الإنفاق المعروضين يستثنيان الطلبات الملغاة.
- **التحليلات**: خمس تبويبات حقيقية محسوبة من نفس بيانات الطلبات/المنتجات/الأقسام/العملاء — **نظرة عامة** (إجمالي مبيعات، عدد طلبات، عدد عملاء، متوسط الطلب، رسم مبيعات ١٤ يوم، أكثر الأقسام مبيعاً)، **المبيعات** (نفس الرسم + تفصيل حسب موعد التوصيل)، **المنتجات** (أعلى ١٠ منتجات إيراداً + الإيراد حسب القسم)، **العملاء** (أعلى ١٠ عملاء إنفاقاً + نسبة العملاء بطلبات متكررة)، **الطلبات** (تفصيل حسب الحالة + نسبة الإلغاء)، **المناطق** (الإيراد وعدد الطلبات مجمّعة حسب محافظة العميل الحقيقية من الطلب — راجع "المحافظة في الطلبات" بالأسفل). كل أرقام الإيراد والمبيعات تستثني الطلبات الملغاة؛ عدد الطلبات وتفصيل الحالات فقط يشملانها.
- **الخصومات**: جدول كل أكواد الخصم (بحث بالكود) مع إحصائيات (عدد الأكواد، أكواد مفعّلة، مرات الاستخدام، أكواد منتهية)، إنشاء كود جديد (نسبة مئوية أو قيمة ثابتة، حد أدنى للطلب، حد أقصى للاستخدام، تاريخ انتهاء)، وتعديل كود موجود (الكود نفسه لا يتغيّر بعد الإنشاء) عبر `/api/admin/discounts`. الكود يُستخدم فعلياً من العميل في `/cart` — راجع قسم "أكواد الخصم" بالأعلى.
- **شرائح العملاء** (`/customers/segments`): تصنيف حي فوق بيانات العملاء الحقيقية نفسها (بدون جدول جديد) — عملاء جدد (آخر ٧ أيام)، متكررون (طلبان فأكثر)، كبار عملاء VIP (أعلى ٢٠٪ إنفاقاً بين من طلبوا فعلاً — نسبة تتكيف تلقائياً مع حجم المتجر، مش رقم ثابت)، في خطر (طلبوا من قبل لكن مش من ٣٠ يوم)، ولم يطلبوا بعد. الشرائح غير حصرية — نفس العميل ممكن يظهر في أكتر من شريحة.
- **المستخدمون والصلاحيات** (`/settings/users`): جدول كل الحسابات (عملاء ومديرين) مع تعيين/إلغاء صلاحية المدير مباشرة من الواجهة عبر `PATCH /api/admin/users/:id/admin` — بديل واجهي لسكربت `make-admin`. الحساب الحالي لا يقدر يلغي صلاحيته الخاصة (لتفادي قفل الوصول بالخطأ).
- **البنرات** (`/marketing/banners`): بانر الصفحة الرئيسية للعميل (`promo-hero`) أصبح بيانات حقيقية في جدول `banners` بدل نص ثابت في الكود — إنشاء/تعديل بانرات (شارة علوية، عنوان، ملاحظة، إيموجي، نص الزر، الرابط الداخلي، الحالة ظاهر/مخفي) عبر `/api/admin/banners`. تطبيق العميل يجيب البنرات الفعّالة فقط من `GET /api/banners` ويعرضها في الرئيسية، مع نقاط تنقّل (dots) لو فيه أكتر من بانر فعّال.
- **الصفحة الرئيسية** (`/marketing/home`): تحكّم حقيقي في إظهار/إخفاء قسمي "عروض اليوم" و"الأكثر مبيعاً" في رئيسية العميل (`show_todays_offers`/`show_best_sellers` في `store_settings`) — نفس النمط المستخدم للحد الأدنى وحد الشحن. صفحتا `/offers` و`/best-sellers` نفسهما تفضلان متاحتين للعميل دايماً بغض النظر عن هذا الإعداد؛ ده بس بيتحكم في ظهورهما كمعاينة على الرئيسية.
- **المتجر والتوصيل** (`/settings/store`, `/settings/delivery`): اسم المتجر ورقم واتساب ورمز العملة والحد الأدنى للطلب وحد الشحن المجاني وتكلفة التوصيل — كل ده بقى صف واحد حقيقي في جدول `store_settings` بدل ملف `src/config/store.ts` (اتحذف)، معدَّل من لوحة التحكم عبر `GET/PATCH /api/admin/settings`. تطبيق العميل يجيبه مرة واحدة عند فتح التطبيق (`GET /api/settings`) ضمن نفس تحميل الكتالوج، ويخزّنه في singleton بسيط (`src/store/settingsStore.ts`) تقرأ منه كل الدوال اللي كانت بتستورد `STORE_CONFIG` قديماً (`formatMoney`, رسالة واتساب, `CartContext`, صفحة السلة, صفحة الحساب).
- **الدفع** (`/settings/payment`): المتجر يقبل الدفع عند الاستلام (COD) فقط حالياً — مفيش بوابة دفع إلكتروني متصلة. صفحة الدفع في لوحة التحكم بتحكّم فعلياً في مفتاح `cod_enabled` في `store_settings`: لو اتقفل، السيرفر نفسه يرفض أي طلب جديد (`POST /api/orders` يرجّع `cod_disabled`) مش بس واجهة العميل، وصفحة الدفع في `/checkout` بتوضّح إن الدفع عند الاستلام متوقف مؤقتاً وتعطّل زر تأكيد الطلب لحد ما يترفع التفعيل تاني. خيار "بطاقة/محفظة إلكترونية" باقي معروض كـ"قريباً" في واجهة العميل زي ما كان.
- **المحفظة** (`/wallet/overview`, `/wallet/txns`, `/wallet/collect`, `/wallet/expenses`, `/wallet/settle`) — كل التبويبات مبنية فعلياً الآن:
  - **نظرة عامة / الحركات المالية / التحصيلات**: بما إن الدفع كله COD، الكاش الحقيقي الوحيد اللي بيتحرك هو نفس بيانات الطلبات الموجودة فعلاً — مفيش جدول جديد لهذه الثلاثة، بتعيد قراءة نفس `/api/admin/orders` وتفسّرها مالياً (إجمالي المحصّل = طلبات "تم التسليم"، قيد التحصيل = طلبات لسه ما اتسلّمتش ومش ملغاة، رسم بياني ١٤ يوم، وجدول حركات/تحصيلات قابل للبحث يفتح نفس لوحة تفاصيل الطلب).
  - **المصروفات** (`/wallet/expenses`): سجل حر بدون فئات ثابتة — جدول `expenses` جديد (فئة نصية حرة، مبلغ، تاريخ، ملاحظة اختيارية) عبر `/api/admin/expenses` (إضافة وحذف). الأدمن بيكتب أي فئة تناسبه (بنزين، صيانة، إيجار...)، مفيش قائمة مقفولة.
  - **التسويات** (`/wallet/settle`): تمثّل تسوية كاش المناديب — جدول `riders` جديد (اسم، هاتف، نشط/متوقف) عبر `/api/admin/riders`، وعمود `orders.rider_id` بيربط كل طلب بمندوب توصيله (يتحدد من نفس لوحة تفاصيل الطلب في أي تبويب، الجديد قسم "المندوب المسؤول عن التوصيل"). المستحق لكل مندوب = مجموع طلباته "تم التسليم" اللي لسه ما اتسوّتش (`orders.settlement_id IS NULL`). زر "تسوية" بينشئ صف في جدول `settlements` (مبلغ محسوب سيرفر-سايد وقت التسوية، مش من المتصفح) ويقفل كل الطلبات المستحقة عليه بربطها بهذه التسوية — فمفيش تسوية تحسب نفس الطلب مرتين. تاريخ التسويات بيتعرض كامل في نفس الصفحة.
  - ملحوظة عامة: التاريخ المستخدم في رسم "الكاش المحصّل" هو تاريخ إنشاء الطلب، لأن قاعدة البيانات حالياً مش بتسجّل وقت تسليم منفصل.

**غير مبني بعد:** تبويب "واتساب" داخل التسويق — ده مش مسألة نقل بيانات من ملف ثابت زي باقي المراحل، ده يحتاج ربط حقيقي بـ WhatsApp Business API (بيانات اعتماد ووصول فعلي) عشان يبعت رسائل تسويقية للعملاء، وده بنية تحتية خارج نطاق نقل البيانات لقاعدة البيانات. رقم واتساب المتجر نفسه (المستخدم في رسائل الطلبات) بالفعل قابل للتعديل بالكامل من `/settings/store`.

## المحافظة في الطلبات

بيانات التوصيل في `/checkout` أصبحت تشمل حقل **المحافظة** (قائمة منسدلة بمحافظات مصر الـ٢٧، `src/data/governorates.ts`) بجانب الاسم والموبايل والعنوان — حقل مطلوب مثل باقي الحقول. القيمة بتتحفظ فعلياً مع الطلب (`orders.customer_governorate`) وتظهر في: تفاصيل الطلب للعميل، رسالة واتساب، لوحة تفاصيل الطلب بلوحة التحكم، وتبويب **المناطق** في التحليلات. الطلبات القديمة (قبل إضافة الحقل) تُصنَّف "غير محدد" بدل ما تختفي أو تسبب خطأ.
